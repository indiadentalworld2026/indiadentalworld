The governing architecture decisions

Before any technology is named, four architectural decisions shape everything. Get these wrong and the stack is wrong regardless of which frameworks you pick.

Decision 1 — Monolith first, microservices later. IDW starts as a well-structured monolith: one deployable application, one codebase, clean module boundaries inside it. When a specific module (search, booking, payments) needs to scale independently, it gets extracted. This avoids the operational complexity of microservices before you have the team to manage them, while keeping the path to microservices clean and low-cost.
Decision 2 — API-first, from day one. Every feature is built as an API first, then a UI is placed on top of it. This means the same backend serves the web app, the mobile app, third-party integrations (insurance, ABDM, lab systems), and future AI agents. No spaghetti, no rebuilds when you need a new channel.
Decision 3 — Data sovereignty, always. All patient health data is stored in India (AWS Mumbai). No health data transits outside India without explicit, logged, patient-consented reasons. This is both a DPDP obligation and a clinical trust requirement. It is baked into the architecture, not added as a policy patch later.
Decision 4 — Open standards over proprietary formats. FHIR R4 for health records. SNOMED CT for clinical terminology. DICOM for imaging. Standard SQL for the primary database. These decisions mean IDW can integrate with any hospital system, any insurance platform, any government health infrastructure — today and 10 years from now. Proprietary formats create prison walls you will spend years escaping.

02

Web frontend

The patient-facing website, the clinic PMS portal, and all B2B portals. One codebase, multiple applications, shared component library.

Next.js 14+ (App Router)Core
React framework with server-side rendering, static generation and incremental static regeneration. Powers the lakh-scale clinic pages as pre-rendered HTML. The only framework that simultaneously solves SEO, performance, and complex app interactivity in one codebase.
Powers Practo, Zocdoc, and every serious healthcare platform built since 2022.
TypeScriptCore
Typed JavaScript across the entire frontend and backend Node.js codebase. Catches bugs before they reach production. Essential when multiple developers work on the same codebase and when the data structures (clinical records, FHIR) are complex and must be correct.
Non-negotiable at scale. Saves ~30% of debugging time in large codebases.
Tailwind CSSCore
Utility-first CSS framework. IDW's design tokens (colours, spacing, typography) are configured once in tailwind.config.js. Every component uses these tokens. A designer changes a colour in one file — it updates everywhere. Eliminates entire categories of CSS bugs.
Fastest way to implement and maintain a design system at team scale.
shadcn/uiCore
Accessible, unstyled UI components that we own and customise. Not a third-party library — the code lives in our repo. Buttons, forms, dropdowns, modals, toasts — all WCAG 2.2 AA compliant out of the box, built on Radix UI primitives.
Eliminates months of component-building. Accessible by default.
ZustandState
Lightweight global state management. Used for: current user session, clinic context in the PMS, booking flow state, offline queue. Simpler than Redux, more predictable than Context API for complex state.
1/10th the boilerplate of Redux. Scales to complex clinic PMS state.
TanStack QueryData fetching
Server state management — handles API calls, caching, background refetching, and optimistic updates. When a dentist marks an appointment complete, the UI updates instantly (optimistic) while syncing with the server in the background.
Makes every API call feel instant. Powers the 5-minute slot availability cache.
React Hook Form + ZodForms
Form handling with runtime type validation. Zod schemas are shared between frontend and backend, so the same validation rules apply on both sides. The booking form, prescription builder, and billing form all use the same source of truth.
Shared validation = bugs caught on the client, never reach the server.
Workbox (PWA)Offline
Progressive Web App service worker library. Enables the clinic PMS to work offline — a dentist can chart, prescribe and bill even when the internet drops. Changes are queued and synced when connectivity returns. Non-negotiable for tier-2/3 cities.
Paper is the competitor. Offline capability beats paper.
03

Mobile app

One codebase for iOS and Android. Same components as the web where possible. Native device features where needed.

React Native (Expo)Core
Cross-platform mobile framework. 90% of the codebase is shared between iOS and Android. Expo provides over-the-air updates — you can push UI fixes without going through App Store review. The component knowledge from the Next.js team transfers directly.
One team, two platforms. Practo, Apollo 247, and 1mg all use React Native.
Expo RouterNavigation
File-based routing for React Native, identical pattern to Next.js App Router. A developer who knows the web codebase can work on mobile immediately with no relearning. Deep linking, universal links, and push notification routing all handled.
Same mental model as Next.js = faster team, fewer bugs across platforms.
Expo Camera + ML KitPhase 2
For guided at-home oral photo scans. Patient photographs their teeth — ML Kit runs on-device analysis and flags changes for the dentist. Zero server cost for basic analysis. Available when the AI roadmap reaches this milestone.
On-device AI = no data leaves the phone for basic oral screening.
Notifee + FCMNotifications
Rich push notifications with inline actions. A patient gets "Appointment in 30 minutes" with Directions and Reschedule buttons inside the notification. A clinic gets "New booking request" with Confirm and View. Firebase Cloud Messaging for delivery infrastructure.
Actionable notifications drive recall completion and booking confirmation rates.
04

Backend API layer

The brain of the platform. Handles all business logic, data access, and external integrations. Built as a structured monolith with clean module boundaries.

Node.js + NestJSCore
NestJS is a structured Node.js framework with dependency injection, decorators, and a module system that enforces clean architecture. It scales from a single server to microservices without rewriting. TypeScript native. Same language as the frontend — one team can work across the full stack.
Used by Adidas, Roche, and Decathlon at millions of requests per day.
REST + FHIR R4 APIProtocol
Standard REST for all internal API calls. FHIR R4 endpoints exposed for health record interoperability — required for ABDM Milestone 2 and 3. Any hospital system, insurance platform, or government portal that supports FHIR can integrate with IDW without a custom integration.
FHIR is the global healthcare data standard. Non-negotiable for ABDM integration.
GraphQL (Apollo Server)Phase 2
For the clinic PMS dashboard where a single page needs data from 5+ tables. GraphQL lets the frontend ask for exactly the data it needs, eliminating over-fetching that slows dashboard load times. Add in Phase 2 after the REST API is stable.
Eliminates N+1 queries that kill dashboard performance at scale.
BullMQ + RedisQueue
Background job queue. Every operation that should not block the user's request goes here: sending a WhatsApp confirmation, generating a PDF invoice, triggering a recall, regenerating a static clinic page after a profile update, syncing with ABDM. Essential for a responsive UI at scale.
Anything slow goes in a queue. The user never waits for a PDF to generate.
Passport.js + JWTAuth
JWT tokens for stateless API auth. Passport.js handles multiple auth strategies: OTP via SMS (primary for India), Google OAuth, ABDM ABHA login. Role-based access control enforced at the API level: patient, dentist, receptionist, clinic admin, vendor, lab, platform admin.
OTP-first auth matches Indian user behaviour. ABHA login is an ABDM requirement.
Zod (shared validation)Validation
The same Zod schemas used on the frontend are reused in the backend API. A phone number that passes client-side validation is guaranteed to pass server-side validation — because they use the same schema. Eliminates an entire class of inconsistency bugs in large codebases.
Single source of truth for every data shape in the system.
05

Database

The foundation everything sits on. The most conservative, most important choice in the stack.

The rule: Never store health data in a NoSQL database. Health records have strict relational integrity requirements — a prescription must always point to a real patient, a real doctor, a real drug. NoSQL databases make these guarantees hard to enforce. PostgreSQL is the right and only choice for clinical data.
PostgreSQL 16+Non-negotiable
The world's most advanced open-source relational database. ACID compliant — every clinical transaction either fully succeeds or fully rolls back, never partial. Supports JSONB for flexible fields (clinical notes, custom procedure data) while maintaining relational integrity. Row-level security for multi-tenant clinic data isolation. PostGIS for geo queries. Used by Instagram, Spotify, and GitHub at billions of rows.
Has been the right answer for healthcare databases for 20 years. Will continue to be.
Prisma ORMORM
Type-safe database client for TypeScript. The schema is defined in one Prisma schema file — from which TypeScript types, database migrations, and the query client are all auto-generated. A developer cannot write a query that asks for a column that does not exist. Catches database errors at compile time, not in production.
Type-safe queries eliminate the #1 cause of runtime database errors.
ClickHouseAnalytics DB
A separate, columnar database for analytics and reporting. The clinic's revenue dashboard, vendor campaign analytics, platform growth metrics — all run against ClickHouse, never against the primary PostgreSQL. Events are streamed from PostgreSQL to ClickHouse asynchronously.
Analytics queries that take 30s on PostgreSQL take 0.1s on ClickHouse.
AWS S3 + CloudFrontFile storage
Object storage for all binary files: clinic photos, X-rays (DICOM), prescriptions (PDF), invoices (PDF), lab case photos, patient consent forms. S3 in ap-south-1 (Mumbai) for data residency. Signed URLs — a file is only accessible via a time-limited, permission-checked URL. Nobody can guess a URL to access another patient's X-ray.
Infinite scale, per-access security, Mumbai region for data residency compliance.
06

Search and cache

ElasticsearchSearch
Powers patient-facing clinic search — by locality, specialty, doctor name, procedure, symptom, and natural language. Start with PostgreSQL FTS. Migrate to Elasticsearch when clinics exceed 50k. Gives: fuzzy matching, synonym handling ("RCT" finds "root canal"), geo-distance ranking, and sub-100ms query times across millions of records.
The only solution that gives sub-100ms search at IDW's target scale.
RedisCache + Queue
Two critical uses: (1) Cache — slot availability (5-min TTL), city-level search results (10-min TTL), clinic profile data (60-min TTL, invalidated on profile update). Prevents the database from being hit on every patient page load. (2) Queue backend — BullMQ sits on Redis for all background jobs.
Slot availability must be live but cannot hit the DB on every page load. Redis solves this.
AlgoliaPhase 1 alternative
Managed search-as-a-service. Faster to set up than self-hosted Elasticsearch. Higher ongoing cost at scale. Use Algolia in Phase 1 to move fast, migrate to self-hosted Elasticsearch in Phase 3 when the monthly bill exceeds the cost of running your own cluster. Build search against an abstraction layer so this migration is transparent to the frontend.
Faster to launch with. Plan the migration path before you start.

AI and intelligence layer

AI is a first-class citizen in IDW's architecture from day one — not bolted on later. Every AI feature is assistive, never autonomous. The licensed clinician always decides.

Python + FastAPIAI service
A separate Python microservice for all AI/ML workloads. Python is the undisputed home of AI/ML libraries. FastAPI is a high-performance async web framework. The Node.js core API calls this service for AI features — keeping AI code cleanly separated from business logic.
Python for AI is non-negotiable. Keeping it separate keeps the Node.js API clean.
Claude API (Anthropic)LLM
Powers: ambient voice charting (spoken notes → structured SOAP note), patient FAQ answering, treatment plan explanation in plain language, search intent understanding ("my tooth is killing me" → emergency + pain specialty filter), dental literature summarisation. Long context window essential for processing full patient histories.
Best-in-class instruction following for clinical text. Long context for patient history.
Whisper (OpenAI)Voice
Speech-to-text for voice charting. A dentist speaks during a procedure — Whisper transcribes in real time — Claude structures it into a SOAP note and pre-fills the chart fields. The dentist reviews and confirms. This eliminates the single biggest barrier to clinical record completeness: gloved-hand typing.
Removes gloved-hand typing. The most impactful single AI feature in the PMS.
Dental X-ray AI (3rd-party)Phase 2
Integrate a CDSCO-cleared dental AI diagnostic tool (Pearl, Apteryx, or Carestream AI) as an assistive second-opinion layer on X-rays uploaded to the EMR. Findings presented as suggestions, never diagnoses. Every acceptance and override is logged for audit and model improvement.
Raises diagnostic confidence. Drives case acceptance. Regulatory review required first.
pgvectorPhase 2
PostgreSQL extension that adds vector similarity search. Used for: semantic search across clinical notes, treatment plan recommendation based on diagnosis history, and matching patient symptom descriptions to the most relevant specialist. Keeps vector search inside PostgreSQL — no separate vector database needed.
Semantic understanding of clinical text without a separate infrastructure dependency.
No-show prediction modelPhase 2
A simple ML model trained on IDW's own appointment data — predicts which bookings are likely to result in a no-show. High-risk appointments trigger an additional WhatsApp reminder 2 hours before. Directly improves clinic chair utilisation, the clinic owner's most-watched metric.
15% improvement in chair utilisation = the most valuable dashboard feature for clinics.

Cloud and CDN

AWS (ap-south-1 Mumbai)Primary cloud
Primary cloud provider. Mumbai region for data residency compliance. Services used: ECS/Fargate for compute, RDS for managed PostgreSQL, ElastiCache for managed Redis, S3 for file storage, SES for transactional email, Route 53 for DNS, ACM for SSL, CloudWatch for logs and alerts, IAM for access control, KMS for encryption key management.
ABDM requires India data residency. AWS Mumbai is the reference region for ABDM integrations.
CloudflareCDN + Edge
Global CDN for static assets and pre-rendered clinic pages. DDoS protection. Web Application Firewall. The 48,000+ pre-rendered clinic profile pages are served from Cloudflare's edge — a patient in Chennai loading a Bengaluru clinic page gets it from the nearest node in milliseconds, zero origin load. Also handles bot detection critical at IDW's scale.
Lakh-scale static pages served globally at near-zero cost. DDoS protection included.
VercelPhase 1 option
Managed Next.js hosting. Zero DevOps overhead for the frontend in Phase 1. Automatic preview deployments for every pull request. Migrate to self-hosted on AWS ECS when the Vercel bill exceeds self-hosting cost (typically around ₹2–3L/month). Build the deployment abstraction so migration is a config change.
Best choice for Phase 1. Plan the migration path at Month 6.
Docker + AWS ECS FargateContainers
Every service (API, AI service, background workers) runs in a Docker container. ECS Fargate manages deployment, scaling and health checks without managing servers. Fargate scales to zero when idle — you pay only for actual compute. Auto-scales during peak hours (evenings, when patients book).
Pay for what you use. Scale automatically. No server management overhead.

Messaging and communications

WhatsApp Business APIPrimary channel
The dominant patient communication channel in India. Booking confirmations, appointment reminders, prescriptions, invoices, recall notices, OTP — all via WhatsApp. Provider: Interakt or AiSensy (both Meta-approved BSPs with Indian support). Conversational flows for booking and rescheduling without a human agent.
90%+ open rate vs 20% for SMS. Indians live in WhatsApp.
AWS SNS + TwilioSMS fallback
SMS as fallback when WhatsApp is unavailable — OTP delivery, critical alerts. AWS SNS for bulk SMS (cheaper at scale). Twilio for reliable delivery with detailed receipts. Every OTP uses SMS as primary (regulatory preference in India) with WhatsApp as secondary confirmation.
OTP via SMS is the regulatory default for authentication in India.
PostmarkTransactional email
Transactional email for: welcome emails, password resets, invoice PDFs, booking summaries, weekly digests for clinic owners. Postmark has the highest deliverability rate in the market. Not used for marketing email — that is handled separately by the growth team (Mailchimp or similar).
Highest inbox delivery rate. Medical emails must reach patients, not spam folders.
Firebase Cloud MessagingPush notifications
Rich push notifications for the mobile app. Clinic gets "New booking" with inline Confirm/View. Patient gets "Appointment tomorrow 10 AM" with Directions button. Dentist gets "Lab case received" with View. Actionable notifications — users act without opening the app. Free at any scale.
Free at any scale. The standard for mobile push notifications globally.

DevOps and CI/CD

GitHub + GitHub ActionsSource + CI
All code in GitHub. Actions runs TypeScript type checking, unit tests, integration tests, schema validation, Lighthouse performance audit, and accessibility checks on every pull request. Nothing merges to main without passing all checks. The CI pipeline is the quality gate, not the developer's memory.
Automated quality gates prevent regressions at scale. Every PR is a production candidate.
GitHub Actions + AWS CodeDeployCD
Merge to main → automated tests pass → deploy to staging → smoke tests pass → deploy to production. Canary deployment for template changes — new clinic page template goes to 5% of traffic first. If metrics are stable, rolls to 100%. If metrics degrade, automatic rollback in under 2 minutes.
A bad template deploy affects 5% of pages for 10 minutes, not all pages forever.
TerraformInfrastructure as code
All AWS infrastructure defined as code. Spin up a complete replica of the production environment for staging in 20 minutes. Disaster recovery: rebuild the entire infrastructure from scratch in under an hour. No manual console clicking — every infrastructure change is reviewed, versioned, and reversible.
Infrastructure changes are code changes. Reviewed, versioned, reversible.
Prisma MigrateDatabase migrations
All database schema changes are versioned migrations — reviewed in pull requests, tested in staging, deployed automatically. No manual SQL scripts. No "I ran this in production but forgot staging" class of bugs. Every developer on every machine has the same schema.
Database changes are code changes. The schema is always in sync across environments.

Monitoring and observability

SentryError tracking
Every unhandled error in the frontend and backend is captured automatically — with full stack trace, user session, preceding API call, and device info. A dentist hits an error in the billing flow at 7 PM → Sentry alerts the on-call developer within 30 seconds with everything needed to reproduce and fix it.
Errors in clinical software must be found and fixed in hours, not discovered by users calling support.
Datadog / AWS CloudWatchInfrastructure metrics
CPU, memory, database connections, API response times, queue depth, cache hit rate — all monitored with alert thresholds. A database connection pool reaching 80% capacity triggers an alert before it reaches 100% and causes downtime. CloudWatch for AWS-native metrics. Datadog for cross-service dashboards when the team grows.
Know about problems before users do. Alert at 80%, not at 100%.
PostHogProduct analytics
Self-hosted product analytics. Tracks: search-to-booking conversion rate, booking completion rate, step where users drop off in the booking flow, which clinic page sections get scrolled past. Privacy-compliant (DPDP) because it runs on your own infrastructure. Feature flags for A/B testing. Session recordings for UX debugging.
Self-hosted = DPDP compliant. Tells you where the product is broken, not just that it is.
UptimeRobot / Better UptimeUptime
External uptime monitoring checks every critical endpoint every 60 seconds from multiple global locations. If the booking API goes down in Mumbai but the server does not notice, an external monitor catches it. Public status page at status.indiadentalworld.com shows real-time uptime — builds trust through transparency and reduces support tickets during incidents.
External monitoring sees what your server cannot. Public status page reduces support load.

The team to build it

Minimum viable team to launch IDW in 6 months. Roles overlap — this is a startup team, not a corporate org chart.

Full-stack lead developer
Phase 1 — Critical hire
Next.js, NestJS, PostgreSQL, TypeScript. This person is your CTO until you can hire one. Must be senior, must know healthcare or be willing to learn it fast. Pay market rate or above — ₹25–40L/yr. A cheap developer on a healthcare platform is the most expensive mistake a startup can make.
Frontend developer
Phase 1
React, Next.js, Tailwind, mobile-first CSS. Works from the HTML prototypes built in Claude — converting them into production React components and wiring them up to real API data. Does not need to figure out what to build.
Backend developer
Phase 1
NestJS, PostgreSQL, Redis, API design, ABDM. Owns the API layer, database schema, ABDM integration, background jobs, and payment integration. Works from the database schema document built in Claude.
DevOps / infrastructure
Phase 1 — 0.5 FTE (freelance)
AWS, Docker, Terraform, GitHub Actions. CI/CD pipeline, infrastructure setup, security configuration, monitoring. Can be a freelancer in Phase 1 — 2–3 days per week is sufficient to get the platform running.
QA engineer
Phase 1 — 0.5 FTE
Manual testing, API testing (Postman), basic automation. Every feature tested before it ships. Clinical software cannot have bugs in billing, prescriptions, or records. Can start as the full-stack lead's secondary focus until the platform reaches 10 clinics.
You — Founder
All phases — Product, strategy, growth
Product decisions, stakeholder knowledge, IDW context, clinic onboarding, investor communication, content operations. Use Claude for all documentation, prototype production, and specification writing. Claude replaces a design agency, technical writer, architect, and content writer in this team.
