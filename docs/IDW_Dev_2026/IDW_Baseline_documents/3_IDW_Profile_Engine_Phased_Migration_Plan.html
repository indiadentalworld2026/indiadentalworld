01

Core migration principle

IDW should not rebuild its existing operational database simply to create a better profile experience.

Strategic decision

Extend first. Replace only where necessary. Migrate incrementally. Preserve production IDs and public URLs. Keep the existing appointment engine untouched unless the audit identifies a genuine structural dependency.

Layer 01Existing production data — dentists, clinics, users, appointments and other sound operational records
Layer 02Canonical data layer — controlled treatments, conditions, relationships and normalized entities
Layer 03Profile Engine — assembles verified data into a single canonical profile
Layer 04Discovery layer — SEO, GEO, AEO, internal linking and structured data
Layer 05Patient experience — responsive profile, CTAs, booking, media, cases and local information
Why this is faster

The platform already contains valuable production data. Reusing stable entities avoids unnecessary data migration, account migration, appointment rewrites and URL disruption.

02

Phase 0 — Database audit & dependency mapping

No new production tables should be created merely because they appear in the target architecture. First establish what IDW already has.

  1. Dentists / doctors. Verify primary ID, identity fields, qualifications, registration information, specialties and profile URL generation.
  2. Clinics. Verify clinic ID, name, address, locality, city, state, PIN and coordinates.
  3. Dentist ↔ clinic. Establish whether one dentist can work at multiple clinics and how that relationship is stored.
  4. Users / authentication. Trace dentist account ownership without duplicating authentication data.
  5. Appointments. Identify every dependency on dentist IDs, clinic IDs, booking URLs, schedules and availability.
  6. Treatments. Determine whether treatments are controlled entities, free text, duplicated records or a mixture.
  7. Cases, media and reviews. Map ownership, storage, moderation and public URLs.
  8. Localities and URLs. Verify geographic normalization, canonical URLs, routing, redirects and sitemap generation.

Schema gap matrix

Hard rule

Do not create duplicate Dentist, Clinic, User or Appointment tables just to support the new profile engine.

Condition layer

Profile FAQs

Responsibilities

  • Assemble profile content from entity relationships.
  • Generate the patient-facing page.
  • Generate canonical metadata and structured data.
  • Generate internal links between dentist, clinic, locality, treatment, condition and case entities.
  • Expose persistent conversion actions: Call, WhatsApp and Book Appointment.
  • Deliver optimized images and videos through the media layer.

07

Phase 5 — Pilot rollout

Use a representative pilot rather than switching every dentist simultaneously.

Pilot cohort

5–20 representative profiles

Include profiles with different specialties, cities, treatment counts, case studies, media volumes and appointment activity.

Observe

Compare old and new outputs

Check data completeness, booking integrity, rendering, mobile UX, page speed, crawlability and structured data.

Fix

Resolve defects before expansion

Taxonomy errors, missing relationships, media issues and conversion problems should be corrected at the engine level rather than manually per profile.

08

Phase 6 — Same URL, new renderer

The safest public transition changes the implementation behind the URL rather than the URL itself.

Example

If an established profile uses /dental-clinic/Vidyaranyapura/Vaishnavi-Dental-Clinic/Dr-Sunitha-Prasad, preserve that public address wherever practical. The new Profile Engine should render the page at the same canonical URL.

Protect during cutover

Existing dentist IDs
Existing clinic IDs
Appointment relationships
Booking URLs and flows
Public profile URLs
Canonical URLs
Existing useful indexed content
Internal links
Avoid unnecessary URL changes

Changing URLs, slugs and database identifiers during the same release multiplies failure points. If a URL must change, use a deliberate permanent redirect and canonical strategy.

09

Phase 7 — Gradual scale-up

Expand in controlled cohorts so production problems can be detected before they become platform-wide.

Stage 1

20 profiles

Validate the complete end-to-end workflow.

Stage 2

100 profiles

Stress-test taxonomy diversity, media and booking relationships.

Stage 3

500 profiles

Monitor infrastructure, indexing and page-generation performance.

Stage 4

5,000+ profiles

Validate scale characteristics before moving to the full eligible population.

Stage 5

All eligible profiles

Complete rollout only after operational, SEO and data-integrity gates pass.

Monitor at every stage

Technical

404/5xx errors, response time, Core Web Vitals, crawlability, canonical integrity and structured-data errors.

Search

Indexing, impressions, clicks, query coverage, crawl anomalies and duplicate-content signals.

Business

Profile views, calls, WhatsApp clicks, directions, appointment starts and completed bookings.

11

Phase 9 — Advanced entity architecture

Add higher-order capabilities after the core profile engine is stable.

Case-study layer

case_studies, case_study_treatments, case_study_conditions, case_study_media

Trust layer

dentist_verifications for identity, qualification, registration, clinic association, contact and address verification.

Taxonomy governance

treatment_suggestions and entity_aliases for controlled expansion without fragmentation.

Profile intelligence

profile_completeness as an internal quality-control mechanism—not a public SEO score.

Media intelligence

Responsive derivatives, descriptive naming, dimensions, aspect ratios, compression state, poster images and CDN delivery.

AEO/GEO relationships

Stronger connections between profiles, localities, treatments, conditions, FAQs and educational content.

12

Rollback & data-integrity safeguards

Every migration stage should be reversible without restoring the entire platform from scratch.

Preserve existing primary IDs.
Use explicit legacy-to-canonical mappings.
Avoid destructive migrations during rollout.
Back up before schema changes.
Version database migrations.
Keep old renderer available during pilot.
Use feature flags or equivalent controlled routing.
Log profile-generation failures.
Test appointment creation and retrieval separately.
Validate canonical URLs before public switching.
Hard blocker

Do not proceed to broad rollout if the new profile engine can create, alter, cancel or misroute appointments as a side effect of profile rendering. Profile presentation must remain safely separated from appointment transactions.

Implementation rule

Extend first. Replace only when necessary. Migrate incrementally. Preserve production IDs and public URLs. Do not perform destructive schema changes during the initial Profile Engine rollout.

Decision summary

The fastest practical route is not a second IDW database. It is an incremental Profile Engine built over the existing production data, with new normalized tables only where the current schema has a genuine gap.
